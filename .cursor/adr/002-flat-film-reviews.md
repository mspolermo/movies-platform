# 002. Плоские отзывы к фильму (без дерева)

- **Статус:** Accepted
- **Дата:** 2026-07-24
- **Участники:** —

## Контекст

В `old-client` создание комментария поддерживало `parentId` (threaded replies). В текущем стеке (`TCommentEntity`, `TCreateCommentRequest`, UI `features/getFilmComments`) — только корневые записи: `title` + `text` к `filmId`, плюс лайки. Продуктовой задачи на дерево комментариев нет: нужны **отзывы к фильму**, не форум/треды.

## Решение

Комментарии = **плоский список отзывов** на фильм.

| Инвариант | Деталь |
|-----------|--------|
| Нет `parentId` / replies | Не в entity, request, ORM, UI |
| Один уровень | Отзыв принадлежит только `filmId` |
| Лайки | Разрешены (`CommentLike` / `toggleCommentLike`) |
| Пагинация | Плоский список (`page` / `perPage`) |

Запрещено без нового ADR:

- Поле `parentId` / nested create
- UI «ответить на отзыв» как тред
- Рекурсивные/tree response-типы для comments

Именование в продукте: **отзыв** (review) к фильму; технический домен/таблица могут оставаться `comment*`.

См. типы: `apps/common/types/entity/comment.ts`, `apps/common/types/request/comment.ts`.  
Клиент: `features/getFilmComments`.

## Последствия

**Плюсы**

- Проще API, UI, пагинация, модерация
- Совпадает с текущим кодом — без миграции схемы и без долга «когда-нибудь дерево»
- Закрывает gap миграции с `old-client` без порта replies

**Минусы / риски**

- Нет дискуссий под отзывом; обход только новым корневым отзывом
- Если позже понадобится тред — нужен ADR + миграция схемы/контрактов

**Поддержка**

- Не возвращать `parentId` «на всякий случай» в DTO/types
- Документацию/legacy-описания с деревом считать устаревшими

## Альтернативы

1. **Threaded replies (`parentId`)** — как в old-client; отвергнуто: нет задачи, лишняя сложность UI/API.
2. **Отдельная сущность Review vs Comment** — избыточно при одном сценарии; naming можно улучшить позже без смены модели.
